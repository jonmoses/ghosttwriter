ghosttwriter v1

Design spec · 2026-11-09 · status: draft

1. Goal

Ghosttwriter is a fork of Ghostty (macOS only) for one person who runs several Claude Code sessions side by side. It adds a workbench around the terminal:

  • A vertical tab sidebar on the left. Tabs are grouped by git repo, and each row shows its Claude color, directory, git state, Claude status and goal progress.
  • A goals panel per session: a short checklist of high-level criteria such as "identify the source of the bug". Both the user and Claude write to it, and every change is logged. The same list answers "did I finish what I was doing in this tab?"
  • A resume dashboard. Closing a tab that has a Claude session records it with a "still to finish" note, so it can be reopened later with claude --resume.
  • A side pane per tab that shows HTML, Markdown or PDF beside the terminal. Small HTML pages appear instead as an inline snapshot card.

2. Context

Today. The user runs stock Ghostty 1.3.1 with TokyoNight Night, macos-titlebar-style = tabs and confirm-close-surface = always. ~/.config/ghostty/tabcolor.zsh assigns each new tab the least-used of Claude Code's 8 session colors (red blue green yellow purple orange pink cyan), exports TABCOLOR, and wraps claude so a new session runs /color $TABCOLOR. Directory and git state come from the shell prompt. Nothing records which tabs are mid-task, and closing a tab loses that context.

The fork. jonmoses/ghosttwriter, cloned with upstream pointing at ghostty-org/ghostty (head 2166b446e, 2026-11-09). The parts this design has to fit into:

  • The macOS app lives in macos/Sources (Swift, AppKit + SwiftUI). Each tab is its own NSWindow in a native tabGroup, controlled by TerminalController. A tab's content is TerminalView, which holds a split tree of SurfaceViews.
  • SurfaceView has a stable id: UUID, a published pwd (from OSC 7 shell integration) and a published title. SurfaceConfiguration has environmentVariables and initialInput, which get passed to the core when a surface is created.
  • The core appends the app's Contents/MacOS directory to PATH in every shell, so a binary placed there can be run by name.
  • Ghostty already draws the Kitty graphics protocol. window-show-tab-bar = never only works on GTK.
  • Build with macos/build.nu and run unit tests with macos/build.nu --action test. Building needs Zig 0.17.0, which is not installed yet.

Claude Code. Hooks receive JSON on stdin (session_id, cwd, hook_event_name, plus fields for each event) and inherit the environment of the shell that launched claude. Output from Claude's Bash tool is captured through a pipe and never reaches the terminal directly. This matters for inline images: see Data flow 4.4.

3. Architecture

Where things live:

  • New code goes in macos/Sources/Features/Workbench/, and upstream files get only small hook-in edits. This keeps git merge upstream/main cheap.
  • The core (Zig) is not changed. Every new behavior sits in the Swift app, the gtw binary and the Claude Code plugin.
  • WorkbenchStore is the single source of truth. It is a @MainActor ObservableObject shared across all windows. Views never write to SQLite themselves, and nothing outside the app touches state.db.
  • Native tabs stay. The sidebar selects and reorders the existing NSWindow.tabGroup and hides its tab bar. Restore, AppleScript, goto_tab keybinds and splits keep working unchanged.
  • A session is the unit of memory, not a tab. Goals, notes and status belong to a session record. A surface points at at most one live session record. Closing the surface detaches the record, and the dashboard reattaches it to a new surface.

4. Data flow

4.1 Hook → status badge

How attach chooses the session record:

  • A record with this claude_session_id already exists (a resume): it is attached to surface S.
  • Otherwise, if S already has a record with no Claude id (the user typed goals before starting Claude): that record adopts the id.
  • Otherwise, if source == "clear" and S's record has a different Claude id: the record keeps its goals and note, takes the new id, and logs a relinked event.
  • Otherwise a new record is created.

4.2 Session status

4.3 Close tab → resume

Closing a whole window, or quitting the app, saves every live session with no sheet. The note is the existing note, or else the unchecked goals as a bullet list.

4.4 gtw show: side pane or inline card

A SnapshotCard is a static PNG, at most 600 pt tall and the terminal's width less 24 pt, anchored 12 pt above the bottom edge of the tab's terminal area. Clicking it opens the file in the side pane, and × or Esc (while the card has focus) dismisses it. Each tab keeps its 3 most recent cards in a stack, newest on top. They don't move with scrollback.

6. Interfaces

6.1 Environment set on every surface

GHOSTTWRITER_SURFACE=<SurfaceView.id.uuidString, e.g. 6F1C…-…>
TABCOLOR=<red|blue|green|yellow|purple|orange|pink|cyan>   # a split inherits its tab's color
GHOSTTWRITER_SOCKET=$HOME/Library/Application Support/Ghosttwriter/gtw.sock

6.2 gtw command line

gtw goal add "<text>"            # prints the new goal's index (1-based)
gtw goal done <index>
gtw goal undo <index>
gtw goal rm <index>
gtw goal list [--json]            # "[x] 1. text" per line
gtw note "<text>"                 # set the session's still-to-finish note; "" clears it
gtw status done|clear             # set or clear the manual done flag
gtw show <file> [--pane|--inline]
gtw color <name>                  # change the tab color; prints "/color <name>" for the user to run in Claude
gtw hook                          # reads Claude hook JSON on stdin and forwards it
gtw info [--json]                 # surface, session record, claude session id, status
global flags: --surface <uuid> (default $GHOSTTWRITER_SURFACE), --socket <path>
exit codes: 0 ok · 1 app reported an error (message on stderr) · 2 usage error · 3 app not reachable
gtw hook always exits 0 and prints nothing.

When a goal command arrives from Claude, the author is claude: gtw sets author:"claude" when the CLAUDECODE environment variable is 1. Otherwise the author is user.

6.3 Socket protocol

The socket is a Unix stream socket at $GHOSTTWRITER_SOCKET with mode 0600. Each connection carries one request: a UTF-8 JSON object terminated by \n. The server sends one reply line and closes.

request:  {"v":1,"op":"<op>","surface":"<uuid>","author":"user"|"claude","args":{…}}
reply:    {"ok":true,"data":{…}}  |  {"ok":false,"error":"<message>"}

op            args                                              data
hook          {"event","session_id","cwd","source"?,"message"?} {}
goal.add      {"text"}                                          {"index"}
goal.done     {"index"}                                         {}
goal.undo     {"index"}                                         {}
goal.rm       {"index"}                                         {}
goal.list     {}                                                {"goals":[{"index","text","done","author"}]}
note.set      {"text"}                                          {}
status.set    {"done":true|false}                               {}
show          {"path","mode":"auto"|"pane"|"inline","tty":bool} {"placed":"pane"|"card"|"tty","png"?:"<abs path>"}
color.set     {"name"}                                          {}
info          {}                                                {"surface","record_id","claude_session_id"?,"status","color","cwd"}

When show answers placed:"tty", gtw itself writes the PNG at png as a Kitty graphics image (a=T,f=100,t=f, base64 path) and then deletes the file.

6.4 WorkbenchStore (Swift)

@MainActor final class WorkbenchStore: ObservableObject {
  static let shared: WorkbenchStore
  @Published private(set) var records: [UUID: SessionRecord]        // live and closed
  @Published private(set) var surfaceRecord: [UUID: UUID]           // surface id → record id
  @Published private(set) var git: [String: GitState]               // repo root → state
  @Published var groupOrder: [String]                               // repo roots; "" = Other
  @Published var pinned: Set<UUID>                                  // record ids

  func record(for surface: UUID, create: Bool) -> SessionRecord?
  func handleHook(surface: UUID, event: HookEvent) throws
  func addGoal(surface: UUID, text: String, author: Author) throws -> Int
  func setGoal(surface: UUID, index: Int, done: Bool, author: Author) throws
  func removeGoal(surface: UUID, index: Int, author: Author) throws
  func setNote(surface: UUID, text: String) throws
  func setManualDone(surface: UUID, _ done: Bool) throws
  func close(surface: UUID, note: String?) throws                   // nil note = discard: delete record
  func reattach(record: UUID, to surface: UUID) throws
  func closedRecords(matching query: String) -> [SessionRecord]      // newest first
  func deleteRecord(_ id: UUID) throws
}

struct SessionRecord: Identifiable { id: UUID; claudeSessionId: String?; surfaceId: UUID?;
  cwd: String; repoRoot: String?; title: String; color: ClaudeColor; status: SessionStatus;
  manualDone: Bool; note: String; goals: [Goal]; createdAt, updatedAt: Date; closedAt: Date? }
struct Goal { id: Int64; text: String; done: Bool; author: Author; createdAt: Date; doneAt: Date? }
enum SessionStatus: String { case idle, waiting, working, needsInput = "needs_input" }
enum ClaudeColor: String, CaseIterable { case red, blue, green, yellow, purple, orange, pink, cyan }
enum Author: String { case user, claude }
struct GitState { branch: String; ahead: Int; behind: Int; staged: Int; unstaged: Int; untracked: Int }

6.5 Storage

File: ~/Library/Application Support/Ghosttwriter/state.db, WAL mode, PRAGMA user_version = 1. Migrations run in order at launch.

6.6 Claude Code plugin

claude-plugin/.claude-plugin/plugin.json      {"name":"ghosttwriter","version":"0.1.0"}
claude-plugin/hooks/hooks.json                SessionStart, UserPromptSubmit, PostToolUse, Notification, Stop, SessionEnd

claude-plugin/shell/ghosttwriter.zsh          claude() wrapper: appends "/color $TABCOLOR" under the same rules as tabcolor.zsh

The skill tells Claude to:

  • add 1 to 4 high-level goals at the start of a task (outcomes, not steps);
  • check a goal only when its outcome has been verified;
  • set gtw note whenever it stops with work left;
  • use gtw show for any HTML, Markdown or PDF it wants the user to look at.

7. Constraints

  1. macOS 14 or later only. No changes under src/ (Zig) or pkg/.
  2. Bundle id com.jonmoses.ghosttwriter, product name Ghosttwriter, Sparkle updates off.
  3. Ghosttwriter reads the same ~/.config/ghostty/config as Ghostty, and adds no new Ghostty config keys.
  4. No native tab bar is ever visible in a Ghosttwriter window. The tab-group order always matches the sidebar order top to bottom, so ⌘1–⌘9 select the 1st–9th sidebar rows.
  5. Sidebar width defaults to 240 pt, can be dragged between 180 and 400 pt, and is remembered in UserDefaults key workbench.sidebarWidth.
  6. Side pane width defaults to 45% of the window, can be dragged between 25% and 70%, and is remembered in workbench.sidePaneFraction.
  7. Shortcuts: ⌘⌥S toggles the sidebar, ⌘⌥P toggles the side pane, ⌘⌥R opens the resume dashboard, and ⌘⌥G focuses the goal add field.
  8. Each sidebar row shows, in order: color dot, title, cwd basename, branch with ↑ahead ↓behind, a dirty marker ● if staged + unstaged + untracked > 0, a status badge, and goal progress "done/total" when total > 0.
  9. Rows are grouped by git toplevel, with the group label being the basename of the repo root. Non-repo tabs go in a group labelled "Other". Pinned rows show only in the Pinned section at the top.
  10. Rows can be reordered by dragging only within their own group. Groups can be reordered by dragging their headers.
  11. Git status refreshes on a pwd change and every 5 s for repos visible in the key window. Each run has a 2 s timeout, at most 4 git processes run at once, and a timed-out repo shows "?" instead of counts.
  12. Status badges: working = spinner, waiting = hollow dot, needs_input = orange "!", done = ✓, idle = no badge.
  13. Colors: a new tab gets the least-used of the 8 Claude colors among live tabs, with ties broken at random. Splits inherit their tab's color.
  14. gtw hook sends at most 64 KB of stdin. It gives up after 500 ms when it can't reach the socket, and always exits 0.
  15. The ControlServer handles each request in under 50 ms on the main actor, not counting show rendering, which runs asynchronously with a 5 s limit.
  16. The close sheet appears only for ⌘W / Close Tab on a tab with a non-idle session that is not done. It replaces Ghostty's own confirm alert there. All other closes save without asking.
  17. The close sheet's note is prefilled with the existing note, or else "- " + each unchecked goal on its own line.
  18. Resuming opens a new tab in the record's cwd with TABCOLOR set to the record's color and the record reattached. If the record has a claude_session_id, the tab also types the initial input claude --resume <claude_session_id>\n. If it has none (goals were typed but Claude never started), no input is typed.
  19. Closed records are kept for 90 days or until there are 500 of them, whichever comes first, and pruning happens at launch. Goal events are deleted together with their record.
  20. Inline rule: HTML goes inline only if the file is ≤ 200 KB, contains no <script, and has scrollHeight ≤ 600 px at a render width of min(terminal width − 24 pt, 1000 pt). Otherwise it opens in the pane.
  21. A tab's SnapshotCard stack holds at most 3 cards. A new card pushes out the oldest.
  22. Side pane reloads are debounced by 150 ms after the last file event and keep the scroll position (HTML/MD) or page (PDF).
  23. Markdown rendering uses bundled markdown-it 14.1.0 and mermaid 11.4.1 from app resources and makes no network requests.
  24. The socket has mode 0600 and the directory 0700. Requests over 1 MB are rejected.

8. Testing

Unit tests live in macos/Tests/Workbench/ and run with macos/build.nu --action test.

  • WorkbenchStoreTests, against a temp-dir SQLite file:
    • every attach rule in 4.1, including clear relink and resume reattach;
    • goal add, check, uncheck and remove, each writing exactly one event with the right author;
    • close then reattach keeps goals and note;
    • pruning at 90 days and 500 records;
    • everything survives reopening the database.
  • StatusMachineTests: every transition in Figure 3, and that "done" is derived correctly from goals plus manualDone.
  • ColorAllocatorTests: least-used choice, the tie set, and splits inheriting.
  • GitPorcelainTests: parses fixture outputs (clean, ahead/behind, detached head, no upstream, untracked only) into GitState.
  • ProtocolTests: each op round-trips through Codable, and unknown ops and bad versions return ok:false.
  • ControlServerTests: a real socket in a temp dir. Covers request and reply, the 1 MB rejection and the 0600 mode.
  • ShowRoutingTests: each branch of Figure 5, with fixture HTML (small static, tall static, scripted, 300 KB).
  • TabGroupBridgeTests: with 5 tabs, select, move and hide keep the tab bar hidden and the order equal to the sidebar's.

gtw tests in macos/Tests/Workbench/GtwTests run the built binary against a test socket server and check argument parsing, exit codes 0–3, the author detection from CLAUDECODE, that hook exits 0 with no server, and that the Kitty escape is written only when stdout is a TTY.

Plugin test: claude-plugin/tests/hooks.sh pipes the recorded hook JSON fixtures through gtw hook --socket into a test server and checks the resulting statuses.

First real use (manual checklist, run once on the built app):

  1. Open 8 tabs across 3 repos plus ~. Check the groups and colors, that no tab bar shows, and that ⌘1–⌘9 match the sidebar.
  2. Run claude in two tabs. The badges go working → waiting live, and a permission prompt shows "!".
  3. Ask Claude to set goals. They appear in the panel with author claude, and the log lists them.
  4. ⌘W one Claude tab, edit the note, save. ⌘⌥R lists it. Enter resumes the same session in the same cwd and color, with goals intact.
  5. Quit the app with 2 Claude tabs open, relaunch, and check that both are in the dashboard with auto notes.
  6. Ask Claude to write a small HTML mockup and gtw show it, which should give a card. Then a long report, which should open in the pane. Edit the report and check that the pane reloads with its scroll position kept.
  7. Run gtw show small.html yourself in a plain shell and check that the image appears in scrollback.
  8. Run git merge upstream/main on a scratch branch and check that conflicts touch only the files in "Upstream files touched".

9. Out of scope

  • WYSIWYG editing of Markdown and HTML, and PDF annotation and form fill. These are planned for v2; the v1 side pane only views.
  • Linux/GTK, iOS, and the Quick Terminal (which gets no sidebar).
  • Live, interactive web views inside the terminal's scrollback.
  • Manual tab groups, and nesting tabs inside other tabs.
  • Syncing state.db across machines, and any network service.
  • AppleScript or App Intents access to workbench data.
  • Parsing terminal output to infer Claude's state: only hooks are used.
  • Upstreaming any of this to ghostty-org.
